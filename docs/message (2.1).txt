  Scenario 1: The Memory Leak Disaster

  What Happened:

  At 2:30 PM during a flash sale, customers start complaining they can't checkout. The ops team gets flooded with alerts.

  The Actual Problem:

  Inventory Service has a memory leak. As it runs out of memory, it becomes slow. This causes Order Service to timeout waiting for inventory checks. Order failures cause Cart Service to show errors. Users see "Something went wrong."

  Timeline of Failure Propagation:
  ─────────────────────────────────────────────────────────────────────────
  2:30 PM  │ Inventory Service memory hits 95% (ROOT CAUSE)
  2:31 PM  │ Inventory Service response time: 50ms → 3000ms
  2:32 PM  │ Order Service starts timing out on inventory checks
  2:33 PM  │ Cart Service gets errors from Order Service
  2:34 PM  │ Users see checkout failures
  2:35 PM  │ Alerts fire for ALL services (Cart, Order, Payment)
  ─────────────────────────────────────────────────────────────────────────

  ---
  How Different Systems Handle This

  ❌ Single-Modal Approaches (Baseline)

  Metric-only (JumpStarter):
  Alert: Cart Service - Error rate spike detected
  Alert: Order Service - Latency anomaly detected
  Alert: Payment Service - Timeout anomaly detected
  Alert: Inventory Service - Memory anomaly detected

  Operator sees: 4 alerts, no idea which is root cause
  Time to diagnose: 45+ minutes of manual investigation

  Log-only (LogAnomaly):
  Alert: "ERROR" detected in Order Service logs
  Alert: "Timeout" detected in Cart Service logs

  Operator sees: Error keywords, but many services have errors
  Problem: Doesn't see Inventory memory issue (no ERROR log)

  │  ────────────────────────────────────────────────────────────────      │
  │  • Discovers: Inventory CAUSES Order timeout (not just correlated)     │
  │  • Builds causal graph with weighted edges                             │

  Scenario 2: The Cascading Database Connection Pool Exhaustion

  What Happened:

  A sudden traffic spike (marketing campaign) causes Product DB connection pool to exhaust. This cascades through multiple services.

  Failure Cascade:
  ─────────────────────────────────────────────────────────────────────────
  Product DB connections exhausted
      └──► Product Service can't fetch products
              └──► Cart Service can't show cart items
                      └──► Order Service can't validate orders
                              └──► Users see "Service Unavailable"
  ─────────────────────────────────────────────────────────────────────────

  DiagFusion vs Our System

  DiagFusion says:
  Root Cause: Product Service
  Failure Type: Connection Error
  Confidence: 0.65
  ❌ Wrong! The actual root cause is Product DB, not Product Service.

  Our System (INGD causal discovery) says:
  Causal Graph Discovered:
  ─────────────────────────────────────────────────────────────────────────

     Product DB ───────► Product Service ───────► Cart Service
         │                     │                       │
     (connection              (API                  (timeout
      exhaustion)            failure)               errors)
         │
         ▼
     ROOT CAUSE
     Confidence: 92%

  Edge Explanation (Product DB → Product Service):
    "DB connection pool at 100/100 connections. Product Service
     waiting for connections, causing 5s delay. Evidence:
     - DB metric: active_connections = 100 (max)
     - DB log: 'Connection pool exhausted, 47 waiters'
     - Trace: ProductService→DB calls timeout after 5000ms"
  ─────────────────────────────────────────────────────────────────────────

  ✅ Correct! Our causal discovery identifies the DATABASE as the true root cause, not the service.

  Scenario 3: The Subtle Configuration Error

  What Happened:

  Someone deployed a config change to Auth Service that reduced its thread pool from 200 to 20. During peak hours, it can't handle the load.

  Why This Is Hard:

  - No errors in logs (just slower responses)
  - No memory/CPU spikes (it's a config issue)
  - Affects ALL downstream services

  The Subtle Problem:
  ─────────────────────────────────────────────────────────────────────────
  Auth Service thread pool: 200 → 20 (config change)
      │
      └──► Auth Service queues requests (no errors, just slow)
              │
              └──► ALL services wait for auth (latency spike everywhere)
                      │
                      └──► Users see slow page loads
  ─────────────────────────────────────────────────────────────────────────

  DiagFusion struggles: Sees latency in MANY services, can't pinpoint Auth.

  Our System (CMEA + INGD):
  ┌─────────────────────────────────────────────────────────────────────────┐
  │  Cross-Modal Pattern Detected (CMEA)                                   │
  ├─────────────────────────────────────────────────────────────────────────┤
  │                                                                         │
  │  Auth Service shows UNUSUAL pattern:                                    │
  │    - Metric: thread_pool_active = 20/20 (100% utilized)                │
  │    - Metric: request_queue_size = 847 (normally < 10)                  │
  │    - Log: No errors (just INFO logs)                                   │
  │    - Trace: Auth calls uniformly slow (not random)                     │
  │                                                                         │
  │  This pattern differs from memory/CPU issues:                          │
  │    - CPU: 15% (low)                                                    │
  │    - Memory: 40% (normal)                                              │
  │    - But thread pool saturated                                         │
  │                                                                         │
  │  CMEA learned: "thread_pool_saturation + queue_growth + uniform        │
  │                 latency = resource_limit_hit (not hardware failure)"   │
  │                                                                         │
  ├─────────────────────────────────────────────────────────────────────────┤
  │  Causal Analysis (INGD)                                                │
  ├─────────────────────────────────────────────────────────────────────────┤
  │                                                                         │
  │  Auth Service ──► Product Service ──► Cart Service ──► Order Service   │
  │      │                                                                  │
  │  All edges have same cause: "waiting for Auth"                         │
  │  Granger causality: Auth latency PRECEDES all other latencies          │
  │                                                                         │
  ├─────────────────────────────────────────────────────────────────────────┤
  │  Final Diagnosis (CCRE)                                                │
  ├─────────────────────────────────────────────────────────────────────────┤
  │                                                                         │
  │  Root Cause: Auth Service - Thread Pool Exhaustion                     │
  │  Confidence: 94% (Calibrated)                                          │
  │                                                                         │
  │  Explanation: Auth Service thread pool is saturated (20/20 threads).   │
  │  This is causing all dependent services to experience uniform latency  │
  │  increases. Unlike memory/CPU issues, the hardware metrics are normal  │
  │  but the application-level resource (thread pool) is exhausted.        │
  │                                                                         │
  │  Likely Cause: Recent config change reduced thread pool size.          │
  │  Recommended: Check recent deployments to Auth Service.                │
  │                                                                         │
  └─────────────────────────────────────────────────────────────────────────┘
